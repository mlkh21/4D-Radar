# Findings

- 当前保护脚本 `run_formal_mini_8gb.sh` 固定旧 full120/p1_04 v1 数据、artifact 与 `formal_mini_chain_v1`，不能验证当前 formal v2。
- 当前 `checkpoint_chain.py` 已定义 `formal_mini_chain_v2`，但 `train_minimal.sh` 尚未接线。
- 当前 formal v2 数据根、garden/loop3 manifest、temporal split、formal data protocol 和 0--80 m normalization artifact 已存在；正式数据只读复用。
- mini 只用于验证数据加载、前向/反向、loss、显存和 checkpoint 闭环，不能作为收敛或正式指标证据。
- `unified_train.py` 当前只把 `formal_chain_v2` 识别为 `formal_multimodal`；若仅把配置改成 `formal_mini_chain_v2`，会绕过 scene/IR/calibration/observed/Radar-statistics/split 门禁并错误进入 legacy temporal split。
- Dataset 已支持显式 `frame_ids_by_scene`，因此无需复制或裁剪正式数据；可在加载正式 split 后确定性截取 train/validation ID，再把截取身份写入 checkpoint。
- VAE checkpoint payload 当前保存完整 `data_protocol`，但没有 mini 选择收据；需要为三阶段共享一个额外、严格校验的 `mini_data_selection` 身份，避免相同 formal data hash 下不同小样本实验被误续训或串链。
- 最小协议做法是把 `mini_selection` 作为 `data_protocol` 的严格扩展：原 split hash 绑定完整有序 ID，`ordered_prefix_per_scene` 加 train/validation 计数即可唯一确定子集；VAE/LDM/CD 现有 payload、resume 和父链相等性检查会自动传播该身份。
- CD unified 入口已把当前 `data_protocol` 传入 trainer，CD payload 也原样保存；无需新增 CD 专属旁路。正式 checkpoint-chain validator 仍只接受 `formal_chain_v2`，因此 mini v2 权重不会被正式链误收。
- formal mini v2 应直接把 Dataset 指向只读正式数据根，并通过 `frame_ids_by_scene` 限制样本；不能继续创建缺 manifest/observed/statistics 的临时软链接数据集。
- 代码审查发现独立 `cd_train_optimized.py::main` 仍用 `checkpoint_protocol == formal_chain_v2` 判断正式训练；`formal_mini_chain_v2` 会因此绕过严格数据配置和 temporal split 加载，属于真实接口分叉。
- `test/mini-test/inference_minimal.sh` 的 formal 分支仍固定旧 p1_04/full120 数据根和 120 m 模型范围；即使 v2 mini 三阶段 checkpoint 正确，后续 smoke inference 也会读取错误的数据几何。
- 推理 run metadata 原先以 normalization 是否 formal 推断 `formal_protocol`，会让 mini checkpoint 看起来像全量正式结果；现改为依据 checkpoint protocol，并单列 `formal_mini_smoke`。严格地图已确认要求 `formal_protocol=true`，因此会拒绝 mini 输出。
- 单模型 `inference_ldm.sh`、`inference_cd.sh` 的 `--deployment_scene_dir` 使用未定义 `SCENE_DIR`；已改为循环内可证明存在的 `${PREPROCESSED_ROOT}/${SCENE}`。
- 最终 formal mini inference 只消费 deployment view 的 Radar/IR 和 Data/config 标定，不自动传 target/LiDAR 真值参数；这条 smoke 只能验证接口，不能产生正式评价指标。
- 用户实际完成 VAE smoke：8 个 batch、1 epoch、5.08 s；loss=5.051657、validation IoU=0.017946、recall=0.750919、precision=0.018053。无 NaN/OOM/异常退出，低 IoU/precision 只能证明训练量不足，不能判断模型质量。
- `vae_best.pt` 内部身份为 `formal_mini_chain_v2`、`formal_data_v2`、0--80 m 网格、ordered-prefix 8/4 选择、latent_dim=4；当前 GPU 已回落到 40 C，smoke 结果应原样保留。
- short profile 应从头写入独立 `test/result/formal_mini_v2_80m_8gb_short_v1/`，避免对已验收 smoke 目录做 resume/覆盖；VAE 固定 3 epoch、运行温度上限 75 C，仍由 20 分钟进程组门禁兜底。
- 保护 runner 的训练核心只通过 `MINI_*_EPOCHS` 传给既有 `train_minimal.sh`，因此 short profile 无需改模型或 Python 训练器；只需在 GPU/输出检查前解析第二个 positional profile 并固定安全参数。
- 现有 fake-GPU harness 把调用参数固定为 `vae`，可小步扩展为可选 `runner_args`，同时保持所有既有测试调用不变；short 行为测试应证明独立结果根、3 epoch/75 C 输出和 `setsid train_minimal.sh vae` 调用。
- 收尾审查发现第三个位置参数会被静默忽略、epoch 日志固定读取 VAE 字段；现改为最多接受两个位置参数并按实际阶段显示，避免未来 profile 扩展形成隐形接口偏差。
- 真实 short preflight 在 RTX 4070 Laptop 上通过：8188 MiB、空闲 6967 MiB、42 C，解析为 VAE 3 epoch、8/4 帧和 75 C 运行门限；artifact/data protocol 校验通过，short 输出根在前后均不存在。
- 原 smoke `vae_best.pt` 在 preflight 前后 SHA-256 均为 `1ae08bf8...c61f50`，证明没有覆盖既有 checkpoint。
- short VAE 已完成 3/3 epoch：loss `5.051601→4.792839→4.690389`，validation IoU `0.017942→0.022273→0.024969`；无 OOM/NaN/异常退出，但绝对指标仍只支持工程 smoke。
- short `vae_best.pt` 为 epoch 3、SHA-256=`a55c0bb0...03510`，state 与 epoch3 逐张量一致，formal-mini/data/grid/8-4/latent 身份完整；原 smoke 哈希未变化。
- LDM preflight 调用链存在真实断点：runner 只检查 `vae_best.pt` 是否存在，`train_minimal.sh` 在 preflight 分支验证 normalization/data protocol 后立即退出；只有 `unified_train.py` 真正启动时才调用 `assert_checkpoint_training_identity`。因此伪造或错协议父 checkpoint 会错误通过“无训练预检”。
- formal garden split 可提供 3210 train、774 validation，足以支持 400/100 或 500/500 两种口径。用户所说“500 帧”必须显式区分总样本与每个 partition，二者 checkpoint mini selection 身份不同。
- short VAE 实测 24 个训练 batch 加 validation 共 14.05 s；按该吞吐线性估计，500 train × 20 epoch 约 5854 s（97.6 min），400 train × 20 epoch 约 4683 s（78.1 min），均与现有 20 分钟门禁不兼容，且 LDM/CD 尚无可靠时长实测。
- 用户确认中型 laptop profile 使用 400 train + 100 validation，总计 500 个互斥 formal split 帧；VAE/LDM/CD 各 20 epoch。服务器使用 3210/774 full split，各阶段同样 20 epoch，不携带 mini selection。
- `train_unified.sh` 现从默认配置继承 VAE/LDM/CD 100/200/200 epoch；正式 launcher 必须显式覆盖 20/20/20，否则用户声明与实际服务器训练不一致。
- `medium_train` 最终固定 400/100、20/20/20、55/72 C、6500 MiB 空闲显存和 180 分钟单阶段上限，并只允许 RTX 4070 Laptop GPU；服务器入口固定 full split 20/20/20 且显式清除 mini frame 字段。
- VAE/LDM 会消费 100 帧 validation；CD 训练调用链只有 train loader，100 帧留出集必须在 CD 后独立评价。中型 profile 改变样本访问次数，不改变每帧 524288 个空间体素、监督或指标公式。
- 用户首次启动 medium VAE 后在 epoch 1 的 batch 50 backward 触发 `CUDACachingAllocator.cpp:2586` 内部断言；错误类型不是 OOM、NaN 或数据异常，失败时 loss=4.4529。保护入口显式导出了 `expandable_segments:True,max_split_size_mb:128`，该 allocator 组合是首要待核对依赖。
- 本机环境为 PyTorch `2.4.1+cu121` / CUDA runtime `12.1`。真实传播链只有 laptop runner 在进程启动前导出 `expandable_segments:True,max_split_size_mb:128`；正式服务器 launcher 仅使用已验证的 `max_split_size_mb:128`。另有 `cm/memory_efficient.py` 在 Python 运行期设置 expandable，但需继续确认 VAE 是否导入/消费。
- 失败 v1 现场只有 `mini_vae_config.yaml`、`vae/training.log` 和仅表头的 `metrics.csv`，没有 epoch/best checkpoint；因此无法从 batch 50 恢复，修复后必须使用 fresh v2 结果根，v1 目录原样保留。
- `cm/__init__.py` 会导入 `memory_efficient` 符号，但尚需核对 line 432 的环境设置是在模块加载期还是显式函数内；无论如何，runner 的进程前 allocator 配置已足以重现当前失败合同。
- `training.log` 只记录训练启动头，`metrics.csv` 只有表头，配置也没有记录 allocator policy；这暴露出一个可审计性缺口：CUDA allocator 是影响运行稳定性的隐藏环境依赖。修复后 runner 至少应固定、打印并测试该值，失败 v1 结果需在索引中明确标为未完成。
- `memory_efficient.py` 的 expandable 设置位于显式函数 `apply_memory_optimizations()` 内，不是模块导入副作用；`unified_train.py` 从 `diffusion_consistency_radar.cm.*` 导入训练组件，而 `train_minimal.sh` 原样继承 runner 环境启动 Python。下一步需确认该函数未被调用，并把 runner 改为与正式 launcher 一致的非-expandable allocator。
- 全仓调用搜索证明 `apply_memory_optimizations()` 没有调用方；本次 VAE 的实际 allocator 唯一来源就是 runner 的导出。最小修复可限定在受保护 runner，不改模型、loss 或训练 Python；失败 v1 应按现有索引规范登记为“失败、无 checkpoint”。
- mini 配置生成器已有 `hardware` 节点，可直接从进程环境记录实际 `PYTORCH_CUDA_ALLOC_CONF`，无需改变 48 参数 shell/Python 接口；正式 launcher 也能在生成 full 配置时记录同一字段。该字段只用于审计，不参与模型或 checkpoint 协议判等。
- 全仓调用搜索确认 `apply_memory_optimizations()` 没有调用者；实际触发源只有 runner 启动前导出的 allocator。修复后 CPU 回归为 103/103 与 20/20，生成配置显式记录 `hardware.cuda_allocator_conf=max_split_size_mb:128`。
- 真实 GPU preflight 读取到 8188 MiB 总显存、6375 MiB 空闲、43°C 且无 compute process；固定 6500 MiB 门槛正确拒绝。当前桌面图形占用约 1407 MiB，需由用户关闭部分图形应用后再做最小 backward 诊断，不能为测试放宽门槛。
